# ContextQA repository implementation backlog

Planning snapshot: October 26, 2026 Pacific time. Applies the supplied GTM brief to the three recently added, authorized `contextqaai` projects. This is a local specification, not authorization to publish source, deploy, spend, contact people, install apps or run paid services. No `indivatools` resources were inspected.

Priority: **P0** makes a first release truthful and useful; **P1** improves activation and commercial learning; **P2** needs demand evidence. Effort is person-days (pd), a planning estimate, not elapsed work already performed. Assign named people to these owner roles before implementation. Shared work is counted once. Do not expand scope simply to satisfy every proposed feature.

## Release acceptance checklist

“Ready” below means a reviewable candidate. No publication/deployment action is authorized by this document.

- **Claims:** every capability/source/signup/pricing/paid feature has register evidence or an explicit unknown. Distinguish local framework, independent pilot and hosted ContextQA. No claim of completed native Layerpath/EkLine integration without actual receipts.
- **Rights:** selected license, dependency notices, contribution/security guidance and unchanged canonical ContextQA logo are reviewed. Real customer screenshots/data are excluded from source fixtures.
- **Usability:** a new tester can inspect sample input and output and run a meaningful local result in the 10–15-minute target; record misses and friction. Core path requires neither account nor LLM subscription.
- **Correctness:** synthetic success and failure fixtures preserve source/run/evidence traceability. Test/assertion outcomes are separate from sequence completion. Partial/unknown outcomes cannot be converted to pass or “verified document.”
- **Safety and cost:** no secret or hidden telemetry; bounded polling/time/steps/concurrency and explicit consequential-action behavior; ordinary CI is local/synthetic. A live run requires documented exact data, approved target, credentials, known charging/stop behavior and separate authorization where necessary.
- **BYOK:** supported protocols, model configuration, content-sharing approval and provider costs are clear. AI-generated narrative remains separate from observed facts; missing usage is unknown; no AI output approves evidence, runs actions or publishes.
- **Evidence:** actual check logs/CI run IDs and limitations are recorded. Do not reproduce stale test counts or call a workflow file a passing run. Target-host security, licensing, onboarding and metering blockers remain visible.
- **Commercial learning:** activation means a meaningful successful live workflow with inspectable result. Repeat use, evaluations and paid conversion have explicit denominators and windows; clicks/stars/local-only sample runs remain supporting signals.

### Experiment decisions (proposed, not results)

- **Continue** when at least 3 of 5 eligible consenting QA teams activate through a meaningful authorized live workflow, at least 2 activated teams repeat, and support/cost are acceptable; separately target 4 of 5 first local results within 15 minutes. A small sample is directional only.
- **Narrow** when a specific source format/recipe works repeatedly but other paths cause most setup or support burden; maintain the working route before adding connectors.
- **Expand** only after at least 2 teams repeat an accepted workflow/update and request the same next recipe, with verified per-success cost and an identifiable buyer. Select at most the three P2 candidates above.
- **Stop or hold live expansion** when required API execution/metering/access remains unavailable, secrets leak, repeated consequential actions cannot be prevented, or support/execution cost exceeds an owner-approved envelope. Keep a useful local toolkit if it stands independently; do not manufacture a paid-ContextQA adoption claim.

### Material open decisions

1. Which documented ContextQA API and account route serves the chosen recipe, and what can actually be executed/retrieved/metered? Existing browser-pilot keys and test-result tokens are separate.
2. Which paid capability is both verified and needed after activation? Until answered, the commercial thesis must keep that clause conditional rather than promise concurrency, retention, trials or enterprise features.
3. Which license and public release scope does the owner approve? The current private prototypes are not already open source.
4. Which one consenting team, target and monthly/live-run budget will validate demand? Existing account sign-in is not permission to expose artifacts or expand app access.
5. Who owns ongoing support, product/API compatibility and a bounded maintenance budget (proposed 2–4 hours/week initially, to be measured)?
